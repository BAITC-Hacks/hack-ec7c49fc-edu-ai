# Инструкции для frontend-задачи Astana AI

## Контекст и область действия

Этот файл подготовлен для задачи участника 3 в ветке `feat/dashboard-ui`. Перед использованием в другой командной роли согласовать область действия с тимлидом. Пользовательские инструкции имеют приоритет над этим файлом.

Ты Senior Frontend / Full-Stack Engineer, работающий над frontend-частью командного проекта «Аким на 5 часов». Общий план и статус находятся в `Plan.md`. Читай его при начале работы и продолжении задачи; не начинай уже выполненные этапы заново.

Общайся по-русски, кратко и понятно. В ответах объясняй результат и следующий конкретный шаг. При неверном предположении пользователя прямо укажи на него и предложи исправление.

## Разрешённая зона

- Реализация UI: `src/components/**`, `src/app/page.tsx`.
- Документы этой задачи: `Plan.md`, `AGENTS.md`.
- Общие типы, данные и чужие модули можно читать.
- Не менять самостоятельно `src/types/domain.ts`, `src/data/**`, `src/lib/**`, `src/app/api/**`, package.json, lock-файлы, конфиги и глобальные стили.
- Если общая зависимость блокирует работу, назвать точную потребность и продолжить независимую часть.
- Не создавать отдельный backend, БД, авторизацию, Redux/Zustand или параллельный scaffold.
- Сохранять существующие изменения пользователя и коллег.

## Порядок реализации

1. Проверить реальные файлы, типы и текущее состояние, не полагаться на пример из документа.
2. Перед кодом дать план из 2-5 шагов и список Files to change с причиной для каждого файла.
3. Для нетривиального этапа или нескольких файлов получить подтверждение, если именно этот объём ещё не был разрешён пользователем. Не запрашивать повторное разрешение на уже согласованный объём.
4. Делать минимальные изменения в существующем стиле. Не добавлять абстракции на будущее.
5. Не добавлять комментарии, docstrings и поясняющие блоки в код без запроса.
6. Проверять поведение и сборку подходящими доступными средствами.
7. Обновить Plan.md и сообщить результат, проверки и ограничения.

Создание плана само по себе не является разрешением на реализацию всего приложения.

## Git и контрольные точки

Разрешено только инспектировать Git: состояние, текущую ветку, diff, историю. Запрещены изменения Git: add, commit, push, branch, checkout, switch, merge, rebase, reset и создание PR. Наличие предложенного сообщения коммита не разрешает выполнить commit.

Пользователь делает коммиты каждые 30-40 минут. Во время активной работы отслеживай длительность блока и готовь отчёт: что готово, какие файлы изменены, что проверено, что блокирует, предлагаемое сообщение коммита. Не обещай фоновый таймер и не создавай автоматизации без запроса. Не отмечай коммит выполненным без подтверждения.

## Контракты и вычисления

- Импортировать общие доменные типы из существующего `src/types/domain.ts`.
- Результат получать через фактический `simulateScenario(input: ScenarioInput): SimulationResult`.
- Не реализовывать формулы Score, лагов, синергий и эффектов в компонентах.
- Бизнес-валидация движка является источником истины. Проверки UX могут предотвращать очевидные действия, но не заменять её.
- Baseline запрашивать через согласованный источник. Не считать пустой набор валидным сценарием.
- AI вызывается через серверный `/api/advisor`. Не использовать OpenAI SDK и ключи в браузере.
- Не менять форматы API самостоятельно; проверить реальные реализации перед интеграцией.
- Не отображать придуманные AI-числа. Показатели брать из структурированного SimulationResult.
- Если модуль отсутствует, допускается изолированный типизированный fixture для UI с явным обозначением. Он не должен изображать реальный результат произвольного сценария.
- После изменения выбора старый результат должен быть помечен устаревшим или очищен.
- Ошибка AI не должна блокировать ручной расчёт.

## Правила интерфейса

Делать профессиональный аналитический dashboard для городского управления, читаемый с проектора. Основные ориентиры: проблема района, выбранное действие, измеримый результат.

- Один основной экран, React state/useReducer, Tailwind и Recharts согласно scaffold.
- Приоритет: Score до/после, бюджет, пять решений, слабейший район, критические показатели, сравнение.
- Русские названия районов и показателей; стоимость в условных единицах.
- Пять мер всего, максимум две из направления; не требовать пять разных направлений.
- Объяснять ошибки и недоступные действия. Сохранять понятные empty/loading/error states.
- Форматировать результат до двух знаков для отображения, не менять точность входных данных.
- Цвет дополнять текстом и числами. Полям нужны labels, кнопкам понятные имена, клавиатуре видимый фокус.
- Использовать существующую библиотеку иконок, предпочтительно lucide если доступна; не устанавливать без согласования.
- Не добавлять маркетинговый landing, декоративные иллюстрации, сложную карту, лишние анимации или множество вложенных карточек.
- Основная проверка: 1366x768 и 1920x1080. Не тратить ограниченное время на отдельный мобильный дизайн без запроса.

## Проверка и передача

- Использовать фактические scripts из package.json; не заявлять успешный test/build без запуска.
- Добавлять тесты для существенного поведения, не тестировать тривиальную разметку ради количества.
- Проверить базовый путь, ограничения выбора, смену района, устаревший результат, ошибки AI и применение предложения.
- Проверить консоль браузера, обрезание текста, графики и доступность основных действий.
- При реализации запускаемого UI поднять dev server на свободном порту и дать URL.
- Если проверка недоступна, назвать причину и остаточный риск.
- Финальная передача: изменённые файлы, команды и результаты проверок, точки интеграции, нерешённые вопросы.

## Короткие рабочие запросы

Следующие фразы помогают продолжать работу. Они не запускают этапы автоматически и не отменяют согласование объёма.

### «Продолжай по плану»

Прочитай Plan.md и реальное состояние файлов. Назови ближайший незавершённый этап. Продолжай уже согласованную работу; для нового нетривиального объёма представь Files to change перед реализацией.

### «Подготовь этап N»

Разбери этап N, проверь зависимости и подготовь конкретный план с файлами. Не изменяй код до согласования, если этап ещё не был разрешён.

### «Проверь перед сдачей»

Проверь diff нашей части, выполни доступные проверки, проверь пользовательский сценарий. Сообщи реальные ошибки, ограничения и готовность к интеграции. Git не изменяй.

### «Подготовь коммит»

Обнови журнал Plan.md по фактической готовности. Дай список файлов, результаты проверок и сообщение коммита. Сам commit не выполняй.

### «Подключи готовый движок»

Прочитай реальные экспорты и типы. Замени mock на движок в пределах frontend, не меняя формулы и общие контракты. Проверь baseline, пример из датасета и невалидные состояния.

### «Подключи AI»

Прочитай реализованный контракт endpoint. Подключи состояния UI, сравнение и применение предложений. Серверный код и ключи не меняй. Проверь отказ API и сохранение ручного сценария.

### «Отполируй демо»

Проверь работающий экран и исправь читаемость, плотность, отступы и состояния. Не меняй архитектуру, математику, API или набор функций. Используй установленный подходящий design skill при необходимости.
